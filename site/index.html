Standfast

Your runner is up. That doesn’t mean GitHub will send it work.

v0.5.0 · unreleased — not yet tagged or downloadable

Why it exists

The token expires. Nothing looks any different.

A runner whose registration has lapsed keeps its process happily running. svc.sh status still says Started. Activity Monitor still shows it. The machine is fine. The next job simply never arrives, and you find out when someone asks why the build has been queued for an hour.

Standfast asks two questions instead of one, and never collapses them. launchd answers whether the process is alive. The GitHub API answers whether GitHub still counts on it. Only the second one decides whether your build runs — so a runner that is up but unreachable gets a state of its own rather than being filed under “stopped”. Different symptom, different fix.

Two surfaces, one model

A quick glance, then the complete Control Center

The menu stays deliberately slim: one row per runner, compact discovery and thermal alerts, freshness, Refresh, Open Standfast, Settings and Quit. Stop, Restart, recent jobs, maintenance, preferences and confirmation dialogs do not compete for menu height.

Open Standfast brings forward one persistent window with one scrolling column of runner cards: state, current work, full service controls, operation feedback, recent history, installed version, logs, and manual disk measurement and safe cleanup stay together per runner.

Operations

Every service request keeps a bounded receipt

Start, Stop, and Restart publish an outcome under the runner they act on. In flight, accepted, uncertain, and failed are different answers.

A command returning means the request was accepted; it does not prove the next probe’s state. A timeout admits the result is uncertain. In-flight feedback remains while the command runs; accepted, uncertain, and failed receipts use a nominal five-minute scan-wall-clock window and are removed by the next normal scan at or after that wall-clock boundary. A system clock correction can shorten or extend that displayed interval; it is not an exact elapsed-time guarantee. Restart can say that Stop completed while its Start phase failed or timed out, so the next action is clear. One runner’s result never overwrites another’s.

Repository runners open their repository’s workflow-runs page. Organization and enterprise runners serve several repositories, so their honest destination is runner settings rather than a registration page mislabeled as run history.

Setup

There is nothing to configure

Standfast finds your runners the way launchd does. It reads the LaunchAgent each runner installed, and the .runner file each one keeps beside itself. No path to type, no repository to name, no token to paste.

~/Library/LaunchAgents/actions.runner.….plist

<key>Label</key>
<string>actions.runner.acme-widget.build-mac</string>
<key>WorkingDirectory</key>
<string>/Users/ci/actions-runner</string>
…and the eight keys we ignore

/Users/ci/actions-runner/.runner

{
  "agentId": 21,
  "agentName": "build-mac",
  "gitHubUrl": "https://github.com/acme/widget",
  "workFolder": "_work"
}

What you need

macOS 14 or later

Standfast runs as a menu bar agent with no Dock icon and no window you have to keep open.

A runner installed as a service

The one ./svc.sh install sets up. A runner started by hand with ./run.sh leaves no LaunchAgent behind, so Standfast cannot see it yet.

The GitHub CLI, authenticated once

gh auth login. Standfast borrows those credentials for its status calls and never keeps a token of its own. Without it, the remote half of every answer reads unknown — and says so, rather than guessing.

When something does not look right

A runner I know exists is missing

It was probably started with ./run.sh instead of installed as a service. Discovery reads ~/Library/LaunchAgents, so a runner with no LaunchAgent has nothing to be found by. If the directory itself cannot be read, Standfast says the reading failed rather than reporting an empty Mac.

Everything says “unknown”

That is the answer when the GitHub half could not be established — usually gh missing, not authenticated, or GitHub not answering. The state carries the reason with it. The local half keeps working, so you still know whether the process is alive.

It says disconnected, but the process is running

That is the exact case this app exists for, and it is not a bug in the reading. The service is alive and GitHub is not counting on it — most often an expired registration token. Re-register the runner; restarting the service alone will not fix it.

The disk is filling up

Open the Control Center and expand Maintenance on the runner. It measures _work and _diag on demand and breaks the total down by what each directory is for. Only the two caches — the tool cache and the downloaded actions — are offered for deletion, and only while that runner is idle or stopped. Repository checkouts are never offered: a workflow may have written files git does not track.

Settings and accessibility

Preferences have a home; status has more than colour

Notifications, SleepGuard, and Open at Login live in a separate native Settings scene, backed by the same long-lived state the app already observes.

The menu-bar item exposes the Standfast name and aggregate value. Runner cards, controls, and operation feedback expose semantic names and values, keep native keyboard order and visible focus, and pair meaningful symbols with text. No state is conveyed only by colour or motion, and v0.5 adds no state animation that needs a Reduce Motion alternative.

The original rounded sentinel/beacon app icon is identity, not runtime status. It has no text or third-party mark and is packaged at every macOS icon size inside the signed resource seal; the menu bar continues to use semantic SF Symbols for live state.

Honest limits

What it will not do

  • It does not manage runners it did not find, register new ones, or edit their labels.
  • It does not support GitHub Enterprise Server yet. That waits on a GitHub client of its own.
  • Anti-sleep holds off idle sleep while a job runs. It cannot keep a laptop awake with the lid closed; macOS offers no public API that could promise otherwise.
  • It does not use sudo. A macOS runner is a per-user LaunchAgent, and nothing here needs more than that.
  • Standfast adds no telemetry. Its functional runner-status and release calls go through the installed gh, which may emit its own pseudonymous telemetry. Standfast uploads no runner logs and never reads or stores credentials; authentication remains with the installed gh, which necessarily transmits its credential to GitHub for authenticated calls.
